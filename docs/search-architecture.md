# Search architecture

Implemented: 2026-08-01 (Phase 10A — restore full Indian market discovery;
Phase 10B — BSE coverage, cross-listing, ranking v2, classification and
listing-status enrichment)

## The regression and its root cause

Multibagger Engine originally allowed searching virtually any Indian listed
stock. During the canonical platform migration (Phases 1–8), search became
tied to the pinned Nifty Smallcap 250 instrument master
(`universes/nifty-smallcap250-instruments.json`) — the only instrument set
ever imported into the canonical identity layer. `instruments.json`, the
static search snapshot the browser fetched, was generated *from that same
250-row master*, and its own warning said so explicitly: "Static instrument
master is limited to the pinned Nifty Smallcap 250 universe." Search,
research and ranking had silently become the same 250-row set. A user could
not find Reliance, TCS, Infosys, HDFC Bank or any other major Indian company
that happened not to be a current Smallcap-250 constituent.

The fix is not a redesign: `mbe.instruments.resolution.InstrumentResolver`
(the dynamic-API resolver) and the client-side `staticSearch()` heuristic
were never artificially scoped to the ranking universe — they scan whatever
identity data exists. The regression was purely a **data-availability**
problem: the search-facing snapshot only ever contained ranking-universe
rows. Phase 10A adds a second, wider identity source and merges it in,
without touching canonical IDs, the resolver's entity-disambiguation logic,
scoring, ranking, or any existing route.

## Three deliberately different universes

| Universe | What it means | Current size | Source |
|---|---|---|---|
| **Search universe** | Everything the platform can identify | 2,947 canonical companies: 2,927 NSE main-board/SME + 20 BSE cross-listings/curated (0 BSE-only) | `mbe.data.nse_search_master` + `mbe.data.bse_search_master` / `universes/{nse,bse}-search-universe.json` |
| **Research universe** | Companies with a deterministic research page | 250 | `universes/nifty-smallcap250-instruments.json` (unchanged) |
| **Ranking universe** | Companies currently scored by the model | 250 (== research universe today) | The current `ModelBuildRow` / weekly `_screener_rows` |

They are separate concepts on purpose, matching how Bloomberg, TIKR,
Finviz and Screener.in behave: **search discovers everything; ranking only
ranks what is currently modeled; research depth depends on available data.**
The research and ranking universes happen to be identical today (250 names)
but are conceptually independent — a future phase could expand ranking to a
configurable universe, or add research pages ahead of scoring, without any
search-layer change. Search must never again be implicitly bounded by
whichever set the ranking model currently covers.

## Search-universe source

`mbe.data.nse_search_master.NseListedSecurityProvider` fetches the same
class of public, documented NSE archive CSV already trusted for official
filings (`nsearchives.nseindia.com`) — not a paid provider, not a scrape of
an uncontrolled site:

- `EQUITY_L.csv` — the full NSE main board (`EQ`/`BE`/`BZ` series).
- `SME_EQUITY_L.csv` — the SME board (`ST`/`SM` series).

`parse_nse_listed_security_csv()` fails closed (`ProviderError`) on a
reshaped or empty source, the same discipline as `mbe.data.universe_nse`. The
pinned snapshot is regenerated with `scripts/refresh_search_universe.py` and
committed at `universes/nse-search-universe.json` (mirroring how
`nifty-smallcap250-instruments.json` is pinned) — the static weekly build and
`api/company.py` never fetch this live at request time.

## BSE coverage and honesty about sourcing (Phase 10B)

`mbe.data.bse_search_master.BseListedSecurityProvider` follows the exact
same fail-closed contract as the NSE provider. During Phase 10B development,
every attempt to fetch BSE's official endpoints from this repository's
network — `api.bseindia.com/BseIndiaAPI/api/ListofScripCodes/w`,
`www.bseindia.com/downloads1/List_Scrips.csv`, several Bhavcopy URL
variants — returned either a bot-protection error page or the site's
client-side-routed app shell instead of data. This was verified, not
assumed (unlike NSE's `nsearchives.nseindia.com`, which is a directly
fetchable static archive). Rather than fabricate broad BSE coverage or
scrape a third-party aggregator, the committed pinned snapshot
(`universes/bse-search-universe.json`, generated by
`scripts/refresh_bse_search_universe.py`) is an explicitly labeled
**curated starter fixture**: `coverage_status:
"curated_starter_fixture_pending_live_verification"`, not
`"live_official_source"`. It contains 20 long-stable, extremely
well-documented large-cap BSE scrip codes (Reliance, TCS, Infosys, HDFC
Bank, ICICI Bank, ITC, SBI, Wipro, L&T, Maruti, Axis Bank, Kotak Mahindra
Bank, Bajaj Finance, Bharti Airtel, HUL, Nestlé India, Sun Pharma, Asian
Paints, HAL, BEL), each cross-checked at generation time against the real
ISIN already verified in the live-fetched `nse-search-universe.json` — the
script refuses to write a row whose ISIN doesn't match. This is a
demonstrable, honest starting point, not a claim of full BSE main-board/SME
breadth (~5,000+ securities); see "Recommended Phase 10C scope".
`scripts/refresh_bse_search_universe.py` tries the live official fetch
first and only falls back to the curated set on `ProviderError` — re-run it
once a reachable official feed exists to replace the fixture with a real
pull, no code change required.

## NSE/BSE cross-listing bridge

No migration was needed: `InstrumentListingRow` already had `exchange_code`,
`bse_code`, `isin`, `is_primary` and `status` columns (Phase 0), and
`stable_instrument_id()` already keys on ISIN alone when present — so a BSE
row and an NSE row sharing an ISIN were already guaranteed to compute the
*same* canonical `instrument_id`. The one real gap: `import_instruments()`
had no code path for "instrument already exists (matched via ISIN) but has
no listing yet on this row's exchange" — it silently did nothing. Phase 10B
adds that branch: it creates a new, non-primary `InstrumentListingRow` for
the new exchange and counts it in a new `ImportSummary.cross_listings_added`
field. Re-importing the same cross-listing is idempotent (no duplicate
listing rows). The exchange that first created the instrument keeps
`is_primary=True`; every other exchange's listing is `is_primary=False` —
this never reassigns primary status on an existing listing.

At the search-index layer, `mbe.search.domain.SearchIndexRecord` gained a
`listings: list[ExchangeListing]` field carrying every exchange's detail
(exchange, symbol, BSE code, ISIN, listing status, primary flag, SME flag).
`exchange`/`symbol`/`bse_code`/`listing_status` still mirror the *primary*
listing for Phase 10A backward compatibility. `mbe.search.catalog.
build_search_index()` gained a `bse_rows` keyword: a BSE row whose computed
ID matches an existing record appends a second `ExchangeListing` (never
overwrites); a BSE row with no NSE match becomes its own BSE-only search
result (`primary_exchange: "BSE"`). Classification reconciliation backfills
`sector`/`industry` from the BSE row **only when the field is still empty**
— an NSE-sourced classification is never silently overwritten — and tags
the field's `sector_source`/`industry_source` as `"exchange_master"` (vs.
`"research_universe"` for the 250 modeled companies). Neither source is
ever inferred from a company name.

Matching this at the DB layer, `mbe.instruments.resolution.
InstrumentResolver`'s `MatchCandidate` gained a `listings: list[ListingMatch]`
field exposing every current listing (not just primary) — Phase 0's
existing BSE-code-on-a-secondary-listing resolution (`test_
bse_code_inactive_and_sme_are_representable`) already matched correctly;
it just didn't surface the full cross-listing detail in the result before.

## Search ranking policy version 2 (`SEARCH_RANKING_POLICY_VERSION`)

`mbe.search.ranking` is now an explicitly versioned policy
(`"2026-08-01.10b.1"`, returned in `search-index.json`'s `meta` and the
dynamic `/api/v1/search/meta` route). It mirrors `InstrumentResolver`'s
tiering exactly (same short-abbreviation protection, same fuzzy threshold
0.78) plus two Phase 10B additions — a full-contiguous-phrase tier and
exchange-aware query parsing:

`exact symbol` (100) → `exact BSE code` (98, checked across *every* listing,
not just primary) → `exact ISIN` (97, likewise) → `exact company name` (95)
→ `alias` (90, or 78 for ≤3-character abbreviations — the Phase 0
disambiguation rule) → `former name` (88) → `full contiguous-phrase match`
(84, new — e.g. "Consultancy Services" inside "Tata Consultancy Services
Ltd", neither a prefix nor the whole name) → `company-name prefix` (82,
reduced for a longer unmatched remainder — this is what ranks "HDFC Bank"
ahead of "HDFC Asset Management Company" for query "HDFC": the remainder
after the matched prefix is one word versus three) → `all-token/word match`
(68, any order, whole tokens) → `fuzzy company name` (60–80, `SequenceMatcher`
ratio ≥ 0.78, skipped entirely via a length-ratio pre-filter when the two
strings' lengths differ by more than half the longer one — see
"Performance").

Bounded tie-breakers apply only *within* an equal score — they can never
promote a worse-tier match above a better one: active listing beats
inactive/delisted/suspended, primary listing beats secondary, main-board
beats SME, and **research/ranking availability is strictly the last
tie-break**, then stable alphabetical/instrument-ID order. A fuzzy match
never outranks an exact match; an unmodeled exact match never loses to a
modeled fuzzy one (both are explicit regression tests).

**Exchange-aware queries**: `mbe.search.ranking.parse_exchange_hint()` (and
its JS mirror, `app.js`'s `parseExchangeHint()`) recognizes an allowlisted
`NSE:`/`BSE:` prefix (`"BSE:500325"`) or trailing whole-word suffix
(`"Reliance BSE"`, `"TCS NSE"`). Only `{"NSE", "BSE"}` are ever treated as a
hint — an arbitrary `"word:word"` shape (including
`"javascript:alert(1)"`) passes through unchanged as a literal query; this
is a bounded allowlist match, not a URI/command parser. When an exchange
hint is present, `rank_search_candidates(..., exchange=...)` excludes any
candidate with **no listing on that exchange** rather than silently
returning it as if it matched there.

Group-company ties (e.g. "Reliance" matching Reliance Industries, Power,
Communications, Chemotex, Home Finance and Industrial Infrastructure — all
legitimately prefix-match) are resolved deterministically by remainder
length, not by market cap: unmodeled companies carry no market-cap signal
to break the tie on. Reliance Industries is guaranteed to be *discoverable*
in that set; it is not guaranteed to be first. Per the Phase 10B spec,
Multibagger Engine deliberately does **not** infer corporate-group/parent-
subsidiary relationships from company names — that's the explicit
"automatic corporate-group inference from names alone" this phase is told
not to do; a `corporate_group` field would need an authoritative ownership
source this phase does not have. See "Known limitations" and "Recommended
Phase 10C scope".

## Listing-status awareness

`SearchIndexRecord.listing_status` (mirroring the primary listing) and each
`ExchangeListing.listing_status` distinguish `active` / `suspended` /
`delisted` / `inactive` / `unknown`. Search ranking treats only `"active"`
as eligible for the "active beats inactive" tie-break — `"unknown"` is
never treated as active. The dynamic `/api/v1/search` route adds
`active_only`, `include_sme` and `include_inactive` query parameters (all
optional, default preserves Phase 10A's unfiltered behavior) so a client
can explicitly exclude delisted/suspended/SME results. Lightweight company
pages show a prominent negative-style badge and a dedicated disclosure
section — not just a quiet status label — when a company's listing is not
active, and never fetch a live quote implication for it beyond what the
existing quote provider already returns.

## Merging: `mbe.search`

- `mbe.search.domain` — `SearchResultType` (`modeled` / `known` / `quote_only`
  / `unknown`, i.e. Type A–D from the product spec), `ExchangeListing` and
  `SearchIndexRecord`.
- `mbe.search.catalog.build_search_index(search_rows, research_instruments,
  screener_rows, *, bse_rows=None)` — the join. Every search-universe row
  gets a canonical `instrument_id` via the same deterministic
  `stable_instrument_id()` used everywhere else. If that ID also appears in
  the research-universe input (`data["instruments"]`, i.e.
  `instruments.json`'s shape), the richer research identity
  (sector/industry/aliases) wins and, if a current `_screener_rows` entry
  exists too, rank/score/confidence/risk are attached — `result_type:
  "modeled"`. Otherwise `result_type: "known"` and rank/score/confidence/risk
  are `null`: **never fabricated**. A research-universe company always
  survives the merge even if a wider source is momentarily missing it.
- `mbe.search.ranking.rank_search_candidates(query, index, *, limit=10,
  exchange=None)` — see "Search ranking policy version 2" above.
- `mbe.search.evaluation` — the deterministic search-quality evaluation set
  (Phase 10B section 20/21); see "Search-quality evaluation" below.

## Where the merge is served

**Static (production today — PostgreSQL is not provisioned):**
`mbe.publish.render_site()` loads the pinned search-universe snapshot (or an
injected override for tests), calls `build_search_index()`, and writes
`site/api/v1/search-index.json` — an additive artifact alongside the
unchanged `instruments.json` (still exactly the 250-row research/ranking
master; its own contract and warning are untouched, so nothing that reads
it today observes any difference). `app.js`'s `staticSearch()` now reads
`search-index.json` instead of `instruments.json` and threads
`result_type`/`research_available`/`rank`/`multibagger_score` through to the
UI for honest badges.

**Dynamic (future, once PostgreSQL is provisioned):** the operator runs the
additive `search-universe-import` CLI command (mirrors `instruments-import`
but *never* passes `--index-code`, so it cannot create or change any
ranking/index membership) to load the same pinned snapshot into the existing
canonical `InstrumentRow`/`CompanyRow` tables. `InstrumentResolver` already
scans every imported instrument regardless of index membership, so
`GET /api/v1/instruments/lookup` (unchanged, backward compatible) sees the
wider universe automatically. Two new additive routes add the honest
typing that `LookupCandidate` doesn't carry:

- `GET /api/v1/search?q=...&limit=...&exchange=&active_only=&include_sme=
  &include_inactive=` — `InstrumentResolver` candidates, each annotated with
  `result_type`/`research_available`/rank/score by joining the latest
  `ModelBuildRow`'s `ScoreSnapshotRow`s, plus (Phase 10B) `bse_code`,
  `primary_exchange`, `listings`, `sector_source`/`industry_source`.
- `GET /api/v1/company/{instrument_id}/summary` — always 200 for any known
  instrument (modeled or not); a live quote via the existing provider
  registry; `ranking_universe_badge`/`scoring_disclosure` populated only
  when `research_available` is `false`; (Phase 10B) the same BSE/listings
  fields as `/search`.
- `GET /api/v1/search/meta` (Phase 10B, additive) — NSE/BSE/cross-listed/
  active/SME counts, research/ranked counts and
  `search_ranking_policy_version`, computed live from `InstrumentListingRow`.

Operators run the additive `bse-search-universe-import` CLI command the
same way — never passing `--index-code`, matches purely by ISIN via the
cross-listing branch above.

**Serverless fallback for canonical company URLs:** `/company/{instrument_id}
.html` stays the permanent canonical route for every company, modeled or
not (`Do NOT change canonical IDs` — none did). The 250 research-universe
pages remain real static files, written exactly as before. Vercel serves an
existing static file before evaluating `rewrites`, so those 250 URLs are
completely unaffected. `vercel.json` adds one rewrite,
`/company/:id.html → /api/company?id=:id`, so any *other* instrument ID —
every company search now finds that isn't modeled — falls through to
`api/company.py`. That function bundles `search-index.json` for identity
lookup, fetches a live quote on demand (never at build time, never on every
keystroke), and renders `mbe.publish.render_lightweight_company_page()`
through the new `company_lightweight.html` template. It refuses
(`404`) to render a `research_available` record, so a static/dynamic
inconsistency fails loudly instead of silently downgrading a real research
page.

## The lightweight (Type B) page contract

`mbe.research.lightweight.build_lightweight_research()` is the single
source of truth for what a non-research company page may contain: identity
(name, symbol, exchange, sector/industry if known, ISIN, listing status),
an optional live quote (price, day change, 52-week high/low — added as new
optional fields on `NormalizedQuote` and threaded through both `api/quotes.
py`'s legacy JSON and the dynamic API's `NormalizedQuote` response), the
fixed badge **"Not currently included in the Multibagger ranking
universe."** and disclosure **"This company has not yet been evaluated by
the Multibagger scoring model."** It raises `ValueError` if handed a
`research_available` record — that function is not allowed to downgrade a
modeled company. Score, rank, strengths, risks, explanations, checklist and
score history are absent from the payload entirely, not blanked: there is
nothing in the template that could accidentally render a zero/placeholder
value as if it were real.

`api/quotes.py`'s whitelist (bounded, not an open proxy) now unions the
published-ticker list with every symbol in the pinned search-universe
snapshot, so a lightweight page's client-side quote fetch works for any
NSE company, not only the 25 previously published picks.

Phase 10B enrichment: the page now shows the BSE code and every exchange
listing (a details/summary table when there is more than one), the primary
exchange, classification source (e.g. "(exchange master)" next to industry)
and a prominent negative-style banner plus dedicated disclosure section
when `listing_status` is not `active` — "Not currently active" — rather
than a quiet label. `build_lightweight_research()` computes an explicit
`is_inactive` flag and `listing_status_disclosure` string so the template
never has to re-derive that logic.

## Search-quality evaluation (Phase 10B)

`mbe.search.evaluation.EVALUATION_SET` is a fixed, versioned list of 16
representative queries — exact symbol, BSE code, ISIN, company name, group
query, short-alias collision guard and an unknown-company negative case —
spanning more than the handful of famous companies used in ad hoc
regression tests, so a ranking change can't silently regress quality
outside that narrow set without a metric moving.
`evaluate_search_quality(index, ranker=rank_search_candidates)` reports
top-1 accuracy, top-3 recall, false-positive count and a per-query
breakdown. Run it with `uv run mbe search-quality-evaluate` (fully offline,
against the real pinned snapshots); it exits nonzero if top-1 accuracy
drops below 100% or any forbidden result appears. Measured result against
the real 2,947-record merged index: **100% top-1 accuracy, 100% top-3
recall, 0 false positives** (see the Phase 10B completion report in
`docs/HANDOVER.md` for the exact run).

## Performance

Bounded-candidate-generation guard (Phase 10B): `_best_match` and its JS
mirror in `app.js`'s `staticSearch()` skip the fuzzy `SequenceMatcher`/
bigram-overlap comparison entirely when the query and candidate name
lengths differ by more than half the longer one — a standard fast-reject
for edit-distance-like measures that cannot possibly reach the 0.78
threshold. Measured effect on the real 2,947-record index: client-side
`staticSearch()` mean latency improved from ~24.5ms to ~16.1ms per query
(Node/V8 benchmark); server-side `rank_search_candidates()` improved from
~66ms to ~35ms mean. Both remain well inside the 180ms input debounce, with
headroom for the "5,000+" design target — no prefix trees, WASM or index
caching were added, matching the proportionate-effort constraint ("do not
turn this phase into a full financial-data expansion project"). Search is
never queried on every keystroke; it runs once per debounce pause.
`search-index.json` is 2.9 MB raw / ~245 KB gzipped for 2,947 records.

## Sector/industry and business-description policy

As of Phase 10C Milestone 1, every classification is tracked with full
source provenance, versioned, and reconciled through a documented priority
rule rather than an inline backfill — see `docs/classification-policy.md`
for the full policy, the no-overwrite-research rule, and measured coverage
numbers (`uv run mbe classification-coverage-report`). In short: neither
the NSE nor the curated BSE source currently supplies a real `sector` value
(`sector_coverage: 0` outside the research universe, which itself has none
either — a pre-existing Phase 0/1 characteristic, not new in this phase).
`industry` is populated for the 250 research-universe companies (source
`"research_universe"`) plus the 20 BSE-cross-linked companies whose curated
fixture carries a real, well-known industry label (source
`"exchange_master"`) — 270 total. Sector/industry are never inferred from a
company name; when absent, the UI shows "Sector unavailable" / "Industry
unavailable" rather than guessing. No business description exists anywhere
outside the research universe — no LLM generation, no company-website
scraping, no competitor-description copying was introduced; the lightweight
page states this plainly rather than inventing prose.

## Offline operations

```bash
python scripts/refresh_search_universe.py           # regenerate the pinned NSE snapshot
python scripts/refresh_bse_search_universe.py       # regenerate the pinned BSE snapshot (curated fallback if live fetch fails)
uv run mbe search-universe-import [--source PATH] [--dry-run]      # DB-backed NSE search (optional; never sets index membership)
uv run mbe bse-search-universe-import [--source PATH] [--dry-run]  # DB-backed BSE cross-listing (optional; never sets index membership)
uv run mbe search-quality-evaluate   # deterministic top-1/top-3 metrics against the real pinned snapshots
uv run mbe search-inspect "HDFC" --limit 5 [--exchange BSE]  # one-query match-evidence debugging aid
```

`scripts/build_site.py` needs no changes: `render_site()` defaults to
loading both pinned snapshots when `search_universe_rows`/`bse_rows` are
not passed.

## Known limitations

- Group-company name collisions (Reliance Industries/Power/Communications/…,
  and similar) are resolved by a deterministic lexical tiebreak, not market
  cap or trading volume — neither is available for unmodeled companies.
  Presence in results is guaranteed; top-of-list position for the "flagship"
  entity in a group is not, until a prominence signal exists (see Phase 10C).
- BSE coverage is a 20-company curated starter fixture (large caps only,
  ISIN-cross-checked against the verified NSE data), not full BSE main-board/
  SME breadth (~5,000+ securities) — BSE's official endpoints were not
  reachable from this repository's development network (see "BSE coverage
  and honesty about sourcing"). No BSE-only company exists in the current
  fixture; the BSE-only code path is exercised only in tests with synthetic
  fixtures. Re-running `scripts/refresh_bse_search_universe.py` once a live
  feed is reachable requires no code change.
- Neither NSE nor the curated BSE source supplies real `sector` values;
  `industry` coverage is 270/2,947 (250 research-universe + 20 BSE
  cross-linked). No sector/industry is ever inferred from a company name.
  Classification is now source-versioned and conflict-tracked — see
  `docs/classification-policy.md` (Phase 10C Milestone 1).
- No corporate-group/parent-subsidiary metadata field exists — the phase
  spec explicitly excludes inferring one from company names alone, and no
  authoritative ownership source was introduced. Group queries return
  multiple relevant results via ranking, not via a dedicated group model.
- The search-universe source has no business-description field. Lightweight
  pages show "Business description unavailable" honestly rather than
  fabricating, scraping company sites, or copying competitor descriptions.
- `api/company.py` fetches identity from the *static* `search-index.json`
  snapshot, so a company newly listed on NSE/BSE since the last weekly build
  will not resolve until the next scheduled build regenerates the snapshot.
- Company summaries in `/api/v1/company/{id}/summary` are always
  `result_type: modeled` once *any* row exists in the latest build's score
  snapshots, using whatever build is `latest_build()` — there is currently
  no per-request specific-build selection on that route (the existing
  `/api/v1/rankings?build_id=` route already supports that where needed).
- Static/dynamic parity is structural (both consume the same
  `build_search_index`/`rank_search_candidates` — the static path always
  does, since PostgreSQL is not provisioned) rather than continuously
  verified between a live database and the static snapshot, because no
  database exists to compare against in this environment.
